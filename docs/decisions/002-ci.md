# 002: Continuous integration

## Context

Three checks must pass before every commit: formatting, clippy with warnings denied, and the tests. Run only by hand, they rely on memory, and a contributor has no way to know they passed.

## Options

- **Toolchain:** latest stable, a pinned version, or a matrix including a minimum supported Rust version.
- **Layout:** one job running the checks in sequence, or a separate job per check.
- **Caching:** `actions/cache` configured by hand, or `Swatinem/rust-cache`.

## Choice

One job on latest stable, on every push and pull request, with `Swatinem/rust-cache`. The steps run cheapest first (format, clippy, tests), so a formatting slip fails in seconds.

`--workspace` is already in the commands so they need no change when the repository becomes a Cargo workspace in Milestone 1. `--locked` makes CI fail if `Cargo.lock` is out of date, so it builds exactly what was committed.

## Trade-offs

- **Stable moves.** A new Rust release can add clippy lints and turn a previously green build red with no code change. That is occasional noise, accepted in exchange for catching new lints early and not maintaining a version pin.
- **No declared minimum Rust version.** Nothing tests older compilers. The Dockerfile also builds on the latest stable `rust:1` image, so the project currently only promises to build on recent stable.
- **Duplicate runs.** `on: [push, pull_request]` runs twice for a pull request from a branch in this repository. It is simple and also covers branches with no pull request open. Limiting `push` to `main` would remove the duplicates if CI minutes ever matter.
- **Actions are pinned by major version tag, not commit hash.** Tags are easier to read and receive fixes, but a compromised tag could run in CI. The workflow's token is read-only, and there are no secrets or deployments for such a run to reach.
